# 디자인 패턴

- 소프트웨어 디자인 과정에서 자주 발생하는 문제들에 대한 전형적인 해결책
- 이는 코드에서 반복되는 디자인 문제들을 해결하기 위해 맞춤화 할 수 있는 미리 만들어진 청사진과 비슷
- 표준화된 라이브러리들이나 함수들을 코드에 복사해 사용하는 것처럼 패턴들을 붙여넣기식으로 사용할 수 없다.
- 패턴은 재사용할 수 있는 코드 조각이 아니라 특정 문제를 해결하는 방식을 알려주는 일반적인 개념
- 패턴은 알고리즘과 자주 혼동. 두 개념 모두 알려진 문제에 대한 일반적인 해결책을 설명
  알고리즘은 어떤 목표를 달성하기 위해 따라야 할 명확한 일련의 절차를 정의하지만, 패턴은 해결책에 대한 더 상위 수준의 설명
  예를 들어 같은 패턴을 두 개의 다른 프로그램에 적용하면 두 프로그램의 코드는 다를 것
- 알고리즘은 요리법에 비유할 수 있지만 패턴은 요리법이 아닌 청사진에 더 가깝다.
  알고리즘과 요리법 둘다 목표를 달성하기 위한 명확한 단계들이 제시,
  청사진은 결과와 기능들은 제시하나 구현 단계 및 순서는 사용자가 결정

## 생성 패턴

- 객체 생성에 관련된 패턴
- 객체의 생성과 조합을 캡슐화해 특정 객체가 생성되거나 변경되어도 프로그램 구조에 영향을 크게 받지 않도록 유연성을 제공

### 팩토리 매서드(Factory Method)

<u>객체를 생성하는 인터페이스</u>를 정의하지만, 인스턴스를 만드는 클래스는 서브클래스에서 결정하도록 하는 패턴

<u>인스턴스를 만드는 것을 서브 클래스</u>

### 추상 팩토리(Abstract Factory)

구체적인 클래스를 지정하지 않고 <u>관련성</u>이 있거나, <u>독립적인 객체들을 생성</u>하기 위한 인터페이스를 제공

### 빌더(Builder)

복합 객체의 생성과정과 표현과정을 <u>분리</u>시켜 동일한 생성과정에서 <u>다양한 표현을 생성</u>

### 프로토타입(Prototype)

생성할 객체의 종류를 명시하는 데 <u>원형이 되는 예시물을 이용</u>하고, 새로운 객체를 이 원형들을 복사함으로써 생성

### 싱글턴(Singleton)

클래스의 인스턴스가 하나임을 보장하고 접근할 수 있는 <u>전역적인 접근점을 제공</u>

디자인 패턴의 <u>가장 많이 알려진</u> 패턴

## 구조 패턴

- 클래스나 객체를 조합해 더 큰 구조를 만드는 패턴
- 서로 다른 인터페이스를 지닌 2개의 객체를 묶어 단일 인터페이스를 제공하거나 객체들을 서로 묶어 새로운 기능을 제공

### 어댑터(Adapter)

클래스의 인터페이스를 사용자가 기대하는 <u>다른 인터페이스로 변환</u>하는 패턴

호환성이 없는 인터페이스 때문에 함께 동작할 수 없는 클래스들이 <u>함께 작동하도록</u> 해주는 패턴

### 브리지(Bridge)

구현부에 <u>추상층을 분리</u>하여 각자 독립적으로 변형할 수 있도록 하는 패턴
